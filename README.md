# 记分簿 Scorebook

给自己的判断记账。一条记录写在知道答案之前，连同当时看的那张 K 线截图一起钉住；
后来市场给了什么，系统再拿真实行情去对。账本写下就不能改——这不是洁癖，是这件事
能不能成立的前提：一本事后可以悄悄改的账，问它什么都只会回答你想听的话。

上手步骤、配置、每一条命令和排障都在 [USAGE.md](USAGE.md)。这一份只讲这东西是
什么、以及为什么做成现在这个样子。

仓库里两棵树：`backend/` 是 Rust 后端（axum + sqlx + PostgreSQL/pgvector），
`frontend/` 是静态 TypeScript/Vite 前端。后端自己的接口清单、代码边界和逐项交付
状态见 [backend/README.md](backend/README.md)，更细的设计与验收证据在
[backend/docs/](backend/docs/)——其中
[history-search.md](backend/docs/history-search.md) 是按图检索那条路的权威说明，
[status.md](backend/docs/status.md) 逐条列着哪些通了、哪些还没通。

## 证据不能改，判断可以改

数据库里 `calls`、`attachments`、`events`、`reviews`、`manifests`、`outcomes`
这些表上挂着一个拒绝一切 UPDATE 的触发器（`migrations/0001_core.sql`）：要修正
就追加一条新的修订或事件，原话原样留着。改了主意不是罪过，假装当初就是这么想的
才是。

这条规矩最清楚的一次表述是
[`backend/migrations/0046_attachment_kind_is_correctable.sql`](backend/migrations/0046_attachment_kind_is_correctable.sql)。
一张截图的字节、尺寸、哈希、上传时间一格都不许动——那是证据；但「这张图当初是
拿来干什么的」是人事后才看得准的判断，当时按同板块对比图传成了 `scene`，事后想
改成 `reference` 就该改得动。所以那一版把整行不可变换成了「只有 `kind` 一列可
改」，别的列一动就抛异常。证据和判断的分界线就画在这里，不在别处。

## 重温和刻舟求剑是两件事

这两个功能都从一张截图出发，但它们要的东西正好相反，文档和代码里都不许混成一件。

**重温**要的是准。一条记录自己说得清是哪个合约、哪个周期，所以它只有一个正确答
案：把这张截图钉回它自己的品种和周期上的那一段真实行情，再从那一刻往后放。品种
和周期是已知的，需要的行情按需去 REST 拉一段就行，判断时刻可能就在昨天，归档里
还没有。

**刻舟求剑**要的是广。它问的是「过去有没有长得像的结构」，任意品种、任意周期——
「哪个合约」恰恰是问题本身，所以它没法按需取数：总不能为了回答这个问题把全市场
所有合约的历史现拉一遍。它只能在一个事先建好的索引里找，那个索引靠
`history.universe` 作业从币安的月度归档扇出来。

分不清这两件事，就会得出「重温能跑，刻舟求剑为什么搜不到」这种假问题——后者搜不
到只有一个原因，那一档周期的索引没建。

## 行情不落盘

公共 K 线、aggTrades 和系统自己画出来的图，一根一张都不写进数据库、任务、日志和
备份。落盘的只有派生向量、来源哈希和时间坐标，`coverage` 里那句
`"raw_market_storage":"none"` 是实话。用户自己传的截图、自己写的原话、自己的真实
成交是另一回事，那是资产，一直留着。

唯一的例外是重温回放：一次回放会把那一段 K 线临时写进 `replay_bars`，带
`expires_at`，退出回放立刻删，worker 每小时兜底清理。它只服务一次展示，统计、结
算、检索一律不读它。这个例外是有意开的，也只开了这一个口子。

## 会做不到就说做不到

没配的组件不降级成别的算法，也不摆一个按不动的按钮：`GET /v1/capabilities` 把
「实现了」「配了」「验收过了」拆成三件事分开回答。Chat 模型没选，适配器就明确返
回 `chat_model_not_configured`；DINOv2 没起，「按画面样子比」就直接说用不了，不
偷偷退回几何那一路假装成功；OCR 没编，品种和周期就要人自己填，绝不从走势形状去
猜。截图检索的周期必须显式给出，缺了返回 `chart_interval_required`——这不是懒得
做自动识别，是猜错周期之后所有比较都是在比不相干的东西，而人不会知道。

匹配分数是结构相似度的排序，不是概率，不是胜率，也不是预测。界面和文档里都不许
把它改名成后面那几样。

## 历史为什么走月档不走 REST

批量建索引只从 `data.binance.vision` 的月度归档取数，一次 REST 都不走。
`backend/crates/infrastructure/src/adapters/binance_archive.rs` 全文没有一处
`budget.reserve`：S3 静态对象不吃交易所接口的限频配额。两百个合约、十年历史这件
事之所以做得动，全部前提就是这一条，把它换成 REST 整个方案立刻不成立。

名单排序是「24 小时成交额名次 + 24 小时成交笔数名次」两项相加后升序。只按成交额
排，几笔巨鲸单就能把一个其实没人交易的合约顶进前列；只按笔数排又会挑出一堆碎单
的小票。名单连同当时的成交额、笔数和两项名次一起存进 `universe_snapshots` /
`universe_members`——ticker 是快照，前 200 名每天都在变，不存档事后就没人答得出
「这一轮到底搜的是哪 200 个、截止到哪一天」。

## 现在到哪一步了

下面是 2026-09-11 当天查库得到的事实，不是承诺。数字会过期，查询不会，
[USAGE.md](USAGE.md) 里有原样可跑的 SQL。

2026-09-11 09:39 UTC 那一刻，已发布的公共特征行按周期是：1d 79,374、4h 43,713、
1h 9,758、30m 1,881、3d 29。币安合约一共 15 个周期，这里只有 5 个有东西，**另外
10 个从来没有建过**。所以「任意品种、任意周期」这句话现在**不成立**：它在 1d 上
是真的，在别处很薄。

真正跑完过的扇出只有 1d 那一轮：200 个合约、401 个工作单元、覆盖 187 个品种，其
中 221 个单元 `complete`、180 个 `partial`。那 180 个不是重跑就能补上的——166 个
是某合约上市晚、照实截断，另外 14 个撞上币安自己的归档缺口（`2022-02` 只到 2 月
25 日、`2022-04` 从 4 月 3 日才开始），缺的那几天在上游就不存在。

4h 的第一轮扇出 2026-09-11 09:31 UTC 排上，中途丢过一次租约、重排之后接着跑；写
下这一段的时候（09:39 UTC）它走到第 13 个品种，**还在跑**。所以上面那个 43,713
你读到的时候一定已经不对了，自己查。1h / 30m / 3d 那点行数不是扇出建的，是
`attachment.locate` 为了定位某张截图、临时围绕判断时刻现建的一小段索引顺带留下
的。

**滚动的历史订阅一条都没有开。** 索引只在人明确排一条作业、或者某次定位现建一段
的时候才增长，不会自己跟着行情往前走。

**匹配质量从来没有验收过。** 没有真实截图标注集，没有测出来的命中率，盲测和大规
模性能验证到写下这句话为止都还没有出数。README 里因此没有任何质量指标——
`backend/docs/history-search.md` 结尾也是这句话，两边是一致的，谁都不要先替它把
话说圆了。

`history.universe` 这条路**没有 HTTP 路由，openapi 里也没有条目**，排队方式是直
接往 `jobs` 表插一行。这是故意押后的入口，不是漏了；具体怎么插见
[USAGE.md](USAGE.md)。

## 这不是什么

这是一个人在一台机器上用的本地系统。一把固定的本机令牌，一个 owner，服务只听
loopback（局域网入口是显式 opt-in 的）。它没有会话、没有多租户、没有按用户的权限
边界，也**没有任何人对它做过面向公网部署的安全审查**。照着 [USAGE.md](USAGE.md)
在自己的 Mac 上跑起来是它被设计的用法；把它放到公网上不是。
