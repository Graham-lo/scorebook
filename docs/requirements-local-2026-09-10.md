# Scorebook｜本机联调新增需求（2026-09-10）

本章依据用户本次直接要求，作为最终任务书的新增生效条款。与旧任务书冲突时，以本章及 v4 实施规格为准。新增产品要求不等于已经验收；状态见文末。

## 一、合约选择：容易找到，默认就好用

- 合约身份以币安实际 USD-M / COIN-M 目录为准，支持加密资产和币安已上线的美股、贵金属等合约；不虚构代码、映射或价格。
- 输入简称 `mu`，`MUUSDT` 应优先于 `ARKMUSDT`、`ARMUSDT` 等仅包含相同字母的合约。顺序为完整代码精确匹配、官方 baseAsset 精确匹配、前缀匹配、包含匹配。
- 支持大小写、首尾空格、全角英文、`MU/USDT`、`MU-USDT`、`BINANCE:MUUSDT.P` 等常见输入；只规范搜索词，保存的品种仍为官方精确身份。
- 未输入时，仍在交易的品种优先，再按币安 24 小时成交额排序。比较成交额而非不同币种的原始枚数；币本位合约按成交张数乘官方合约面值。
- 行情仅经 REST 读取，短时内存缓存并合并并发请求；不得写入数据库、文件或备份。供应商失败明确报错，不退回旧数据源或伪造热门榜。
- 连续输入只允许最后一次查询更新列表；旧请求不能覆盖新结果。加载、无结果、失败、重试、中文输入和键盘选择均需清楚。
- 分页须遵守排序；热门顺序变化时要求重开列表，不能默默重复或漏项。

## 二、按图索骥：两种来源，统一入口

目标是用现在的一段走势结构，寻找过去相似的结构，再研究它后来怎么走。相似结果是复盘参考，不是上涨概率、胜率或交易建议。

1. **我的记录库**：检索已记录的现场截图，返回原始判断、对应截图与复盘入口。
2. **币安公开历史**：检索选定品种、周期、日期范围中已发布的结构特征，返回历史 K 线片段，实时取数绘图。

用户可以选择或扩展品种、起止时间和支持的周期，不能把体验示例中的几个品种或近 90 天写死成产品限制。范围只受币安真实可取得数据、显式资源预算及已发布覆盖约束。大范围拆成任务，支持进度、暂停、继续和追加更早历史。未准备范围不能冒充已搜索；全部历史尚未建成时必须照实说明。

截图上的品种仅是原图信息，不自动限制跨品种搜索。**周期必须明确，识别结果供用户确认，无法识别时必须手动选择，两个搜索来源均只匹配同周期。** 不能从形状猜币种或周期。

## 三、匹配质量优先，结果少而有用

- 用户明确接受较慢的执行，质量优先于抢先显示未经验证的结果。
- 默认展示 **3 个品种**，可选择 5 或 10；历史模式每个品种只保留精排后最接近的一个片段，避免同一品种霸屏。
- 向量召回后重新取回候选 K 线，核对来源哈希与完整性，再比较方向、转折、回撤、实体和影线等结构。
- 候选阶段为各品种留出名额；最终去重在精排之后进行。未精排结果不能标成最终结果。
- 默认保持方向，反向匹配由用户显式选择。结构接近程度不能表达为胜率。
- “最接近”指本次已准备范围和声明预算内找到的候选，不承诺数学意义上币安全部历史的全局最优。
- 无可靠匹配或来源缺失时给出真实原因，不为了凑满数量返回伪造案例。

## 四、历史后续走势：先匹配，再揭示

- 每个最终结果实时绘制一张连续图，明确分为「参与匹配的历史片段」和「该片段结束后的走势」。使用清楚的分界线与淡色区域。
- 默认显示后续 64 根，允许切换 32 / 64 / 128 根；保留品种、周期、匹配起止时间和来源。
- **后续走势不得参与候选召回、匹配评分或结果排序。** 不能按后来涨得好、跌得多来反向挑样本。
- 只展示币安确实存在的已收盘历史 K 线。接近现在时不补未来；数据缺口、缺失归档或来源订正须如实说明。
- 重绘沿用候选指定的 REST / 官方归档来源，不能因一个来源失败偷偷更换另一个来源。
- 原始 OHLC 与生成 SVG/PNG 只存在内存；允许保存用户原图、特征向量、来源哈希、窗口坐标及业务记录。

## 五、从记录到复盘的流程引导（新增待实现）

主线：**记录判断 → 持续观察 → 查看结果 → 完成复盘 → 沉淀做法**。

| 环节 | 用户需要明白的事 | 主要动作及边界 |
|---|---|---|
| 记录判断 | 我当时看到了什么，为什么这样想 | 先写一句或贴图即可保存；标准、方向或期限不完整时说明不能自动判分，不强迫补表 |
| 持续观察 | 当前进展、待触发或等待期限、还缺什么 | 看后续行情、按图找历史、补充证据、设提醒；原话不覆盖 |
| 查看结果 | 市场实际怎么走，是否有足够证据判断 | 原规则结果与实际执行分开；缺数据/未触发/待人工处理各自明确 |
| 完成复盘 | 当时逻辑哪里好、哪里错、下次怎么改 | 草稿自动保存并可恢复；发布绑定所见结果版本；结果变化提示重新核对，不抹掉旧复盘 |
| 沉淀做法 | 这次经验是否值得复用 | 关联情境或打法版本，可选；不自动把一条复盘升级成已验证策略 |

每条记录展示当前环节、完成情况和一个明确的下一步入口。流程是引导而非强制审批链：没有正式评价标准的随手记录可以直接写复盘；不必每条都创建打法；观察期间也能写阶段性复盘。后端提供统一状态依据，前端不另写评分/分母/结算规则。

按图找历史放在观察和复盘两个环节。未来 Chat 可以理解用户意图，调用同一组受权限约束的工具读取记录、账本、统计和相似案例；写入仍需用户明确确认。

视觉要求更新（2026-09-10）：用户明确认为当前页面太工程化、方框过多、缺少色彩和动态效果，要求显著更现代、更漂亮。保留既有业务与接口，允许重做信息架构、页面构图和视觉系统；不再以“沿用已有设计”为限制。建立明确的品牌色、中文排版层级、轻盈材质、自然过渡与完整微交互；减少卡片套卡片，使用时间线、阅读区、分组列表和重点图表。首页、记录、搜图和复盘都须改善，而非只换圆角、阴影或首页皮肤。兼顾深浅主题、键盘、窄窗口、减少动态效果及运行性能。普通页面不展示运维控制台、工程术语或技术审计大屏。具体前端执行要求见桌面《Scorebook_Claude前端重构Prompt_v4.1.md》。

## 七、架构与职责更新

Rust / Axum / Tokio / SQLx + PostgreSQL 17 / pgvector 为主业务架构，独立本地 OCR、DINOv2、BGE-M3 推理进程。取代早期 Python/SQLite 主架构、行情落盘及完全不使用模型的旧条款。Chat 的真实供应商尚未确定；核心记录、账本和评分不依赖 Chat。

Claude 负责现有前端设计与对接；Codex 在用户授权范围内审查、部署并修复联调问题。保持模块化，不建立旧算法、旧模型或其他行情供应商 fallback。多用户产品与已取消的 P6 仍不在本轮范围。
