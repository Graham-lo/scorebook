## 1. 本次范围与固定原则

用户已确认：**前端和多用户体系都先不做。** 不安排页面设计、组件、注册登录、团队协作、计费、租户集群或跨区域部署。现有本机认证、权限检查和 owner 字段保留，保护个人数据；不为省事拆掉已有边界。

完成剩余个人后端能力：可靠搜图、币安历史覆盖、交易导入、完整结算与统计、Chat 和长期备份。原任务书中的 Python/SQLite、行情快照落盘等旧技术要求，已被用户后续明确选择的 Rust/PostgreSQL/行情不落盘取代，不恢复旧实现。

固定原则：

- 主业务继续使用 Rust；PostgreSQL 17 + pgvector；复用已有任务、租约、批量写入、导出恢复和复盘接口。
- Python 仅负责视觉/OCR/文本编码推理；本机截图桥使用小型 Swift 适配程序。结算、账本、统计、权限全部在 Rust。
- 公共 OHLC、aggTrades、系统重绘 SVG/PNG 不写数据库、文件、日志、消息队列或备份。历史归档只在有界内存中解压计算，不用临时目录偷偷缓存。
- 用户截图、文字、真实交易账本属于用户资产，可以持久化；公共行情只保留派生向量、业务计算结果、时间坐标、覆盖信息和输入哈希。不能把逐根行情换个表名当成“特征”保存。
- 行情参考只用实际存在的币安 USD-M/COIN-M 合约。交易执行场所另存，不能把币安参考价格当成其他交易所真实成交价。
- 不保留旧 fallback。更换实现使用显式迁移、校验与一次切换；新能力故障就返回明确状态，不退回旧模型、旧协议或其他供应商。
- 后端能力完成与真实数据接通分别验收；不能用 Mock、合成向量召回率或“已有接口”代替真实功能验收。

## 2. 模块组织和实施顺序

保持四个 Cargo 包，不增加一组互相调用的微服务。把新领域规则放 `core/domain`，用例放 `infrastructure/application/<业务>/`，外部适配器放 `infrastructure/adapters`，HTTP 和模型工具共用用例。

|---|---|---|---|
| P0 | `capabilities`、`contracts` | 原任务书缺口对照、供应商能力表、持久化边界、真实测试集和容量预算 | 现有 v3 |
| P1 | `chart_analysis`、`chart_search` | 自动识别截图、多尺度搜图、结构精排、人工质量验收 | P0 |

| P3 | `trade_import`、`trade_ledger` | 交易所/账单导入、成交账本、交易轮次、与判断和打法关联 | P0 |
| P4 | `trigger_monitor`、`statistics`、`baselines`、`verdicts` | T3 持续监控、完整集合统计、B1、人工裁决及打法验证 | P0；执行统计依赖 P3 |

## 4. P1：让“按图索骥”成为可靠的日常功能

### 4.1 截图分析

新增 `POST /v1/chart-analyses`，输入原图 ID、可选原图像素 ROI；返回主图区域、图表类型、可辨认品种/周期、K 线根数估计及范围、遮挡/清晰度、每个字段的置信度和分析版本。

流程：主图检测 → 坐标轴/副图分离 → 蜡烛几何提取 → 归一化 → 结构描述子。OCR 用于读取画面上确实存在的文字，不能只凭走势形状断言品种或周期。未知周期保持 null，并在检索中展开已声明的周期集合。

首版明确支持普通蜡烛图；平均蜡烛、砖形图、纯线图等先识别类型并给出支持状态，不套用普通蜡烛的价格语义。自动 ROI 不改用户原图；用户可提交明确区域重新分析，不自动切换旧识别器。

### 4.2 检索和精排

唯一的新生产检索协议命名为 `chart-match-v2`，它描述完整流程而非某一个编码模型。内部模型身份、预处理和排序版本分别冻结。

- 私有复盘库：结构向量和已锁定的 DINO 视觉向量召回，合并候选后做几何精排；不同原图与已确认 episode 去重。缺必需模型时明确不可用。
- 公共历史库：优先由内存 OHLC 直接提取统一结构特征，避免每个历史窗口都先绘图再跑 DINO。候选阶段最多 3,000 条；按时间相邻窗口聚合，再对前 30 个候选区域精排。
- 精排检查走势方向、转折位置、回撤比例、波幅关系、实体/影线结构；使用带约束的时间对齐。默认不把上涨和下跌互当匹配，反向结构必须是请求明确选择的模式。
- 历史精排所需 K 线按候选合并区间从币安实时取回，只留内存；不能把第一次取回后的 OHLC 作为长期缓存。展示时仍使用现有即时重绘接口。
- 窗口初始支持 64/128/256 根；截图根数不明确时做多尺度查询。不能通过任意拉伸，把明显不同结构都变成近似匹配。
- 返回匹配依据、限制、模型/语料版本和源 ID。只显示结构相似性，不生成上涨概率或胜率。

计算超过交互预算时返回可取消的 `search_run_id`，通过查询/事件接口继续取结果。过程中的近似候选明确为 provisional，最终列表必须完成该协议规定的精排；不能在模型或行情失败后把未精排结果标成最终成功。

### 4.3 索引切换

新特征仅写独立的新代；验收阶段旧服务仍使用现有唯一活动代，测试工具显式访问新代，不做生产双读或暗中融合。新代完成后暂停相关写入、补齐变更、校验数量与来源，再原子切换活动指针并删除旧运行分支。失败保持新功能未启用，不建立“新失败就退旧”的运行路径。历史导出保留来源身份，过期旧特征按明确迁移规则移除。

### 4.4 质量验收

使用至少 200 张有使用权的真实用户截图，覆盖配色、缩放、密度、画线、压缩和遮挡。100 张用于调参与100 张盲测；同一个原始图及其变体必须放在同一组，禁止把相邻行情窗口同时作为训练和独立测试证据。候选标注池包含多种检索结果与负样本，不只标现有算法返回的图。

以下是计划门槛，不是已取得的结果：

| 指标 | 门槛 |
|---|---|
| 普通可读蜡烛图区域识别 | 至少 90% 的测试图 ROI IoU ≥0.90 |
| 品种/周期自动填写 | 只自动接受高置信识别；精确率目标 ≥98%，同时报告覆盖率和拒识率 |
| 人工相关性 | 对库中确有相关样本的盲测，Top10 命中率 ≥85%，nDCG@10 ≥0.75；另外报告无相关样本查询 |
| ANN 算法召回 | 每个指定筛选强度分别报告 Recall@20，平均目标 ≥95%；列最低值，不能只报总平均 |
| 端到端性能 | 本机私有库搜图 P95 ≤3 秒；历史候选响应 P95 ≤3 秒，含外部取数的完整精排目标 ≤15 秒，分别报告网络耗时 |

若不达标，继续改同一新流程；不靠隐式换模型过验收。真实行情产生的测试图在线生成后释放，保存标签、请求位置、算法版本和摘要，不保存系统图数据集。

## 5. P2：全历史覆盖、增量和容量

### 5.1 “全部历史”的可核实定义

定义为：某次目录版本中实际发现的币安合约、指定周期与窗口网格内，供应商仍能取得的历史区间。目录、可取得范围、已索引范围、暂缺范围和永久不可取得范围分别记录。覆盖到全部日期不等于枚举任意根数、每个起点的所有切片；每次结果带窗口和步长分辨率。

新增 `instrument_lifecycles`、`history_availability`、`coverage_segments`、`history_subscriptions`、`source_revisions`。清单保存品种状态、上市/退市信息、已确认的起止范围、检查时间和归档校验身份，不保存公共行情正文。

每日刷新合约目录，结合官方归档目录保留退市标的，不能仅依赖当前 exchangeInfo。新合约建立新范围；退市只停止在线增量，不删除已有派生历史或用户记录。订正数据产生新代，不在原代上无声覆盖。

### 5.2 固定取数分工

- 历史批量构建：按计划中声明的官方归档单元或 REST 时间片处理。
- 最近已收盘增量：REST；在线触发另用 WebSocket。
- 重绘/精排：指定品种、区间实时读取。

每个任务先保存明确的 source_plan，失败重试同一计划；需要改变来源类型时创建显式修订。归档下载、解压、窗口重叠数据都受内存上限约束，超限拆分任务或报告不支持，禁止自动 spill 到磁盘。校验完成前只写未发布特征；归档缺文件不直接记为无行情。

增量只处理已完成 K 线，保存最后连续完成游标及跨块窗口所需的起止坐标；重启时重取重叠区间。复用现有 500 行块写、代际发布、暂停/恢复/取消和租约机制。全目录订阅拆成每批不超过200个品种的现有计划，子区间仍最多512个窗口起点；不能通过订阅入口绕过已有队列容量限制。

### 5.3 阶段覆盖和容量门槛

先用 10 个常用合约、90 天、1h/4h 验证端到端；随后覆盖目录中全部可取得的 1h/4h/1d；再扩大到 5m/15m，最后构建 1m。每一步都仍是向完整范围推进，响应不得把阶段完成叫作所有范围完成。

窗口 64/128/256 根的初始步长为16/32/64根，精排再检查候选附近的偏移。更密网格必须写进计划与容量估算，不能在后台无限增加存储。

容量公式：每个实际品种/周期分别计算 `max(0, floor((N-W)/S)+1)`，再按模型和窗口相加。下面只是统一假设300个品种各有3年完整数据的示例，并非当前币安真实规模；忽略边缘窗口的近似计算如下：

| 周期范围 | 约需结构向量 | 仅192维 float32载荷 |
|---|---:|---:|
| 1h/4h/1d | 111万 | 0.80 GiB |
| 再加5m/15m | 1,491万 | 10.67 GiB |
| 再加1m | 6,665万 | 47.67 GiB |

还需表行、HNSW、元数据、建库空间和备份余量，不能拿最后一列当总占用。P0/P2 用实际10万/100万窗口测 `pg_total_relation_size`、写入吞吐和CPU耗时，再给出真实计划的磁盘与小时数估算。当前本机不能预先承诺全周期、全品种、全历史都能低延迟驻留内存。

### 5.4 pgvector 扩展方式

保留 pgvector，不同时维护另一套向量数据库。公共库扩大前按 market+interval 分区，使用分区内的模型表达式索引；元数据和关联键同步迁移。分区唯一键需包含分区字段，外部稳定ID通过 locator 查询，不能丢失代关联或留下悬空外键。

不要为每个 symbol 自动建立一个独立部分索引。测试必须包含无筛选、品种筛选和极窄历史截止条件；若分区后仍不满足门槛，停止扩大范围，先调整同一索引方案或目标资源。大范围跨分区查询有界并发、统一合并、明确候选预算。[pgvector 官方过滤与分区说明](https://github.com/pgvector/pgvector#filtering)

新增 `POST /v1/history/plans/estimate`、`POST /v1/history/subscriptions`、`GET /v1/history/catalog`；扩展 coverage 返回目录版本、已知缺口、待建范围和新鲜度。只有请求范围各段都达到终态，才返回该范围的完成状态；不可取得范围必须单列。

验收：新增/退市品种、空文件、429、校验失败、供应商订正、跨分区查询、建库中断全部可恢复；密集建库期间复盘保存 P95 ≤200ms、读取 P95 ≤150ms。ANN 测试之外再验证窗口定位与重绘身份。

## 6. P3：交易导入、账本与复盘关联

### 6.1 取数边界

第一适配器为币安 USD-M，其次 COIN-M。保留通用 `ExchangeHistoryProvider` 端口；其他交易所必须分别实现和验收，不能仅换 base URL 就声称支持。

三种明确入口：近期 API 增量、官方历史导出、用户账单 CSV。CSV 是用户主动选择的导入来源，不是 API 失败时偷偷切换。普通成交接口要求 symbol，发现范围来自既有账本、账单、可用账户活动线索及用户声明的品种范围；逐品种记录覆盖，不能用“当前无持仓”推断没有历史交易。

连接凭证保存到 macOS Keychain，数据库只存凭证引用。适配器只实现读取成交、订单及资金流水；不提供下单、撤单、转账或提现入口。官方导出请求超时但状态未知时保留请求身份，等待核验，不重复消耗月度额度。

### 6.2 数据和批量写入

新增 `exchange_connections`、`import_runs`、`import_coverage`、`execution_fills`、`account_ledger_entries`、`position_cycles`、`execution_links`、`reconciliation_results`。

原始交易凭据不可变；导入文件可以按用户资产保存，去掉凭证字段。每个 fill 使用交易所+账户+产品+symbol+来源成交ID作为唯一身份，CSV也要使用可复现的行身份和文件哈希。订单不是成交，资金流水不是K线，不能混表。

每块500—1,000条，用 COPY staging→校验→集合式合并；游标与本块提交在同一事务推进。重复导入、重叠时间窗、乱序、同毫秒多笔、部分页失败都不重复计入。

### 6.3 交易轮次与核对

- 区分单向持仓与双向持仓；双向按 LONG/SHORT 分账，不把同时存在的两边合成净仓。
- 支持部分成交、加仓、减仓、反手、强平及未平仓。反手成交按实际数量拆成旧轮次平仓部分和新轮次开仓部分。
- 从零仓到再次归零定义一个完整轮次。导入从中途开始时标记 opening_unknown；不能虚构开仓成本。期初仓位必须有账单或其他明确证据。
- 成交盈亏、手续费、资金费、其他账务调整分别计算。法币折算不是原始事实；缺历史换算数据时保留原币种和缺口，不补0。
- USD-M线性和COIN-M反向合约采用不同的合约/乘数与结算币种规则；先核对原币种交易所账单，再输出估值展示。
- 实际成交使用执行交易所价格。币安图仅作为复盘参考；来源不同就分别展示来源，不用参考K线反推真实滑点。
- 用已有独立资金费流水，不能对 fill.realizedPnl 重复加减。不能把所有资金费按时间粗暴塞给某个策略轮次；无法明确归属时保留未分配账项。

判断、episode、打法与执行的联系用显式关联事件维护。系统可以建议相关记录；只有被确认的关联才参与执行统计。后补的复盘不能追认成事前采用；改单通过追加事件保留历史。

新增连接/同步/导入/成交/轮次/核对接口，均返回覆盖和缺口：`/v1/exchange-connections`、`/v1/imports`、`/v1/trades`、`/v1/trade-cycles`、`/v1/reconciliations`、`/v1/execution-links`。

验收：同一账单/API区间重复3次，总成交数、数量和金额不变；按来源精度核对已实现盈亏、手续费、资金费；不一致必须逐项可解释，不能通过“其他调整”抹平差额。覆盖乱序、反手、双向、币本位、未知期初和多币种费用。

## 7. P4：完整结算、统计、背景参照和裁决

### 7.1 T3 持续监控

新增 `trigger_watches`、`trigger_checkpoints`、`trigger_events`。按合约和周期共享行情订阅，不为每条判断单独订阅。主进程、租约和已确认事件使用现有任务机制。

两种明确口径：bar_close只接受提交后合格收盘；trade_touch接受可证明先后关系的合格成交。WebSocket负责在线事件，REST/已声明的历史归档计划负责进度校验与补齐，价格政策不因传输方式改变。[币安 K线流说明](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/Kline-Candlestick-Streams)

触发只允许每分支一次。实际触发时刻、实际参考价、后续到期时间和提交时冻结ATR分别记录；越过价位时不能用阈值价冒充真实参考价。触发前波动不计入触发后的MFE/MAE。

只持久化触发事件、计算结果、连续覆盖游标和摘要哈希，不保存成交流/K线流。重连后先补齐断点再推进；有未证明的缺口时不能宣布“整个窗口未触发”。供应商故障保持处理中；已证实必要证据无法取得时才结束为数据不足，并附固定原因。

### 7.2 完整复盘与知识语义

补齐当前基础表之外的正式业务流程：标签定义/别名映射版本、冷热标签身份、episode固定窗口建议与确认、call与episode级复盘、形成来源记录、打法状态变化、计划采用与执行证据、提交时反馈快照。

所有后补分类有发生时间，不改结算。版本产生案例不计作该版本的后续验证。计划引用不自动变成实际执行；没有执行证据保持 unknown。筛选接口补齐规则允许的路径、立场、来源、采用方式和结果条件，不能只靠前端过滤一页数据。

### 7.3 正式集合与统计

新 `set_definitions`、`set_runs`、`set_sample_members` 按完整筛选构建集合，不要求调用者先枚举全部ID。按后台批次生成固定快照和统计投影，每个数字都有同一 set_snapshot_id 下的成员分页入口。

冻结模板及版本、阈值方式、期限/日历、方向、价格政策、分类身份、归组方式、结果版本选择政策。默认取当前正式 outcome head，规则回放不进入正式成绩。绝对价位不同不必自动拆成不可比集合，但合并规则必须预先声明。

输出 call/claim/episode/代表数、六种业务状态、独立的处理状态与缺口、明确结果分子分母、MFE/MAE中位数、事件时间分布、排除与删除数量。代表样本在看结果前选定，不能挑每段最成功的一条。无分母返回null；金额与比率统一Decimal政策。

### 7.4 B1 背景参照和人工裁决

B1先严格完成原任务书规定的T1背景参照，T2—T5不套T1数字。采样起点在当前判断之前250天范围内，必须整个后续观察期在提交前结束；每个历史起点独立计算当时ATR。同方向、同期限与同端点政策逐条计算，再对各call参照等权汇总。保存样本身份和派生结果，不保存输入K线；没有有效样本返回null。

“所有行情用币安”不自动改写原有期限语义。既有记录沿用冻结日历；新规则明确自然小时或声明的交易日历，不能按 ticker 名称猜。旧任务书要求的美股交易日参照要在真实对应合约和明确日历下验收；不能把自然日结果贴成交易日结果。

新增持久化 verdict_requests/verdict_events：达到20个明确代表，或上次决定后新增20个，去重创建请求。最近10个明确结果低于同集合全期至少20个百分点仅生成复查提示。人工决定 evidence/observe/drop，系统不代填；模型建议也不能自动成为正式裁决。

新增 `/v1/statistics/runs`、`/v1/statistics/runs/{id}/members`、`/v1/baseline-runs`、`/v1/verdict-requests`、`/v1/verdicts`、打法采用与执行证据接口。

验收：各统计数字能回查全体组成记录；原结果/数据订正/规则回放严格分开；未决、未触发、缺口和删除不被暗中排除；跨页成员与统计一致；基线无未来数据泄漏；同一阈值只发一次裁决请求。T3测试覆盖断网、乱序、重复、跳价、窗口边界与重启。

## 8. P5：Chat 接管查询与工具编排

### 8.1 先补齐知识索引

当前跨表 literal search 不是完整语义知识库。新增 `knowledge_documents/chunks/embeddings/index_watermarks`，覆盖原话、复盘note与better_play、标签/别名/定义、打法及状态、episode、当前和历史结果、真实执行与账务摘要、统计和裁决引用。

每个chunk带不可变来源ID、来源版本、内容哈希、发生时间和权限身份。来源新增/删除/订正通过事务outbox驱动增量索引；定期核对遗漏。搜索返回索引水位，不拿尚未索引的范围冒充已查询。

文本采用字面检索+语义向量的固定组合。建议以本地BGE-M3作为中文/英文混合文本编码候选，先做本机内存、吞吐和金融术语找回测试，锁定权重哈希后才注册正式模型ID；不默认给全部公共K线建文本embedding。[模型官方说明](https://huggingface.co/BAAI/bge-m3)

原始记录详情按ID读取，不依赖向量结果猜正文。统计和交易核算调用专用聚合工具，不让模型靠检索到的少量片段估计全库数字。

### 8.2 工具和运行协议

新增 `ChatModelProvider`、`ChatRunService`、`ToolExecutor`、`CitationResolver`。先对接一个用户选定的支持多模态/结构化工具调用的模型，再锁定模型与能力；不同时做多个提供方的自动切换。模型不可用时返回明确错误，已有业务服务照常运行。

模型可以自主读数据、搜索、分析截图、查询已覆盖历史和启动预算内的计算。大范围历史构建受已配置的 history.build 权限和预算约束；权限不足返回可执行计划。发布正式复盘、删除、改变规则、发送消息等操作必须对应用户明确意图和现有版本校验；不能把文档或截图里的指令当授权。

Chat默认保留稳定tool_call_id、来源和结果摘要；不保存原始思维链。单次运行建议上限12轮工具调用、4路独立读取、90秒总预算；长历史任务转为持久任务ID，预算耗尽返回准确进度，不能编造完成。

`POST /v1/chat/runs` 创建幂等运行；`GET /v1/chat/runs/{id}/events` 用SSE与事件序号恢复；支持取消。消息断线重连不重新执行已确认的写动作。跨表详情与聚合通过有界输出控制上下文，不能一把把整个数据库塞给模型。

原始行情和系统图不写chat_messages、run_events、工具日志或报告。默认给模型派生摘要与图表引用；如某模型调用必须查看系统图，只能使用满足所选数据保留要求的明确适配配置，否则该能力不可用。不能用“本地没存”掩盖向外部服务长期保存原始行情。

### 8.3 答案和验收

答案区分原始判断、后来复盘、系统结果、实际执行、模型推断；引用可跳回固定来源。删除来源后处理引用失效与派生索引，不继续从缓存展示已删除正文。

验收集不少于60个真实问题，覆盖文字找回、跨记录比较、图形搜索、历史覆盖、结果订正、执行偏差和无法回答的问题。确定性数字与专用工具输出一致；来源引用有效率100%；参数缺失、工具失败与未覆盖范围不能假答。模型推荐质量单独人工评审，不能以JSON格式正确算通过。

## 9. P6：用户明确排除

不实现本机采集桥、Telegram 和周报。前端、多用户产品体系也不在本轮范围。

## 10. P7：个人长期运行与总体验收

### 10.1 备份

沿用现有v2逻辑归档与校验，加入BackupService调度、保留策略和restic加密备份目标。首次完整备份，随后按内容去重；不把重复压缩整包当成“增量”。备份恢复和完整性检查复用已有归档验证。[restic官方介绍](https://restic.readthedocs.io/en/stable/010_introduction.html)

默认每30分钟备份个人知识库、交易账本与相关原图，保留48个半小时快照、7个日快照、4个周快照；只有远端/独立磁盘已确认完成后才推进备份水位。公共历史向量可重建，备份其目录、版本和计划即可。密钥与业务归档分开管理，恢复说明明确需要哪些Keychain材料。

源文件在备份期间按精确引用保护；只有元数据快照引用的全部原图已复制并校验成功，该次备份才标记为可恢复完成。磁盘/目标不可用保留上一次成功备份并报告，不能清理到只剩失败副本。独立备份盘未配置时只能算本机副本，不能通过设备损坏恢复验收。

在目标可用的前提下，个人不可再生数据恢复点目标≤1小时（30分钟调度间隔，加不超过30分钟的备份完成时限）；恢复时间目标≤2小时，以实际数据量演练为准。公共索引重建耗时另列，不纳入原图/记录已恢复的假定。

### 10.2 运行预算

复盘读写、在线触发、查询、交易同步、历史建库和备份使用显式优先级和独立并发额度，全部纳入CPU/内存/磁盘/出口总预算。历史归档带宽也必须限速，不能只限制REST weight。

只有一个个人使用者也要做背压：Chat一次可以生成很多工具调用，历史构建也可能占满数据库。沿用有界请求/任务队列和搜索许可，容量不足返回明确状态，不能无限创建tokio任务。

### 10.3 最终通过条件

- 本机真实环境连续2小时混合运行：记录/草稿、搜图、行情重绘、交易同步、T3、历史建库、周报生成与备份同时参与；报告接口P50/P95/P99、错误率、队列积压和资源峰值。
- 期间终止API、worker、视觉进程，模拟数据库短断与供应商429/缺口；已确认记录不丢、交易不重复、触发不重复、正式结果不串版本。
- 对原图、交易导入和备份做损坏注入与隔离恢复；删除后全部新增派生表、Chat引用和报告引用按规则处理。
- 在数据库、文件、队列、日志和备份中检查公共行情/系统图的持久化禁区。
- 每阶段完整更新OpenAPI请求与响应类型、契约示例、错误码和真实端到端测试；新增响应不继续只用通用JSON掩盖字段缺失。
- 真实截图语义质量、真实账户核对、真实通知发送与恢复演练分别标记验收结果，不能用56项既有测试通过抵消新增能力未接通。

## 12. 交付口径
