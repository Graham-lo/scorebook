# 按图查找历史走势

当前采用 chart-match-v2。截图搜索必须明确周期，缺失返回 `chart_interval_required`；支持币安合约 klines 的全部 15 个周期：1m/3m/5m/15m/30m/1h/2h/4h/6h/8h/12h/1d/3d/1w/1M（区分大小写，`1m` 是分钟、`1M` 是月）。普通截图中的周期无法可靠识别时，必须由用户选择。OCR 提示不代替确认；不得从走势形状或上一张截图猜周期。

## 搜索流程

上传用户截图及可选 ROI，调用 `/v1/chart-analyses` 读可见文字和蜡烛几何。`/v1/chart-search/runs` 创建有明确 interval 的 private 或 binance_history 检索；worker 再次校验周期，所有候选 SQL 使用同周期等值条件。

历史路径从直接 OHLC 提取 candle-geometry-v2 的 192 维向量；个人记录路径使用几何和 DINOv2 两路，不自动降级。几何会将片段规范到 64 个采样点，向量用于初筛，详细比较使用规范化开高低收位置和有限时间错位对齐。分数是结构排序，不是预测概率。

向量候选预算为 3,000，物化后最多检查前 1,000 条，为每个合约保留最多 3 个不紧邻的片段，并选最多 300 个（`RERANK_BUDGET`，2026-09-12 从 100 抬上来；个人记录那一侧另算，是 `PRIVATE_RERANK_BUDGET` 的 30，因为它每条要跑一次视觉模型）做真实来源核验和精排，结果里的 `rerank_budget` 报的就是这一轮实际用的那个数。公开那一支同时取 6 组月档（`REFETCH_CONCURRENCY`），但那只是这一支自己的宽度，总量闸门在别处，见《取数的形状》。公共结果最后按分数排序，每个合约保留最佳片段，默认 3 个；前端提供 3/5/10。个人记录按原图和已确认记录组去重，未知周期记录不混入。

人看过候选并说「都不是」时，那几条的 id 下一轮以 `exclude` 传回来（公开历史里是 `public_market.features` 的窗口 id，个人记录里是附件 id，结果条目自己带的那个 id 就是要写回来的东西）。排除写在 ANN 取数那一条 SQL 里——候选 CTE 的 `id<>ALL(...)`，**在 `LIMIT 3000` 之前**生效，不是查完之后再在内存里滤：滤在后面得到的只是同一批答案的短版本，而人要的是补上三条没看过的。`exclude` 是累加的，先去重再看上限，最多 100 条（`MAX_EXCLUDE`），越界 422；空列表时 `<>ALL('{}')` 恒为真，请求体与 SQL 行为跟从前逐字节相同。重温那一侧的「都不是」是另一件事——它改的不是这一轮的候选而是搜索范围，见 docs/replay-spec.md §1.7。

## 窗口档位、不定长精排与分数校准（2026-09-12）

窗口档位是 **64 / 96 / 128 / 192 / 256** 五档，不再是 64/128/256 三档（`history::LOCATE_WINDOWS`）。补 96 和 192 的理由只有一个：人截的图落在这两处附近时，最近的一档差出 50%，形状被拉伸到认不出来；补齐之后任何根数到最近一档的偏差都不超过 ±25%。查询时**只查最近的两档**（`history::nearest_windows`）——五档全查是五倍的 ANN 开销，而差出一档以上的窗口本来就不会排到前面。单品种那条路径（`history.rs` 的 ANN SQL）从这一天起也带 `bars_count` 过滤，从前它不过滤，32 根那种边角料窗口会混进候选。

精排改成**不定长**：候选给的是一个窗口坐标，但截图的真实根数很少正好等于某一档，所以取回这段行情之后在 `n ± 15%`、步长 4 上逐根滑一遍取最像的一段（`chart_search/rerank.rs::best_window` → `chart_match::sweep`），红绿两种假设各扫一遍取高者。返回的起止时刻是扫出来的那一段，不是索引里那一档的边界。

**分数没有量纲，稀有度才有。** 0.63 分是高是低，取决于同一个周期同一个根数上随便两段行情能撞出多少分。`chart_match_calibration(interval, bars_bucket, sample_score)`（迁移 0052）存的就是这个分布：`chart.calibrate` 作业从 `public_market.features` 里随机取样本窗口，逐个拿它自己去检索（排除它自己那一段），把 top1 的分数记下来，几百条就够把分布量出来。查询时 `Calibration::load` 一次把这个周期的整条分布读进内存，逐条结果算 `rarity`＝这一档里低于它的样本比例；`level` 按 0.97 / 0.85 / 0.6 分成 `sure` / `likely` / `weak`，低于 0.6 不给词。**没有校准数据不是错误**：`rarity` 为 `null`，`level` 退回按绝对分 0.75 / 0.6 / 0.45 分档，用的是同一组词，免得同一张图在校准数据到位前后跳两个不同的说法。整轮结果另给一个 `verdict`（`found|weak|none`）。这些全是枚举值，不是文案——中文怎么说是前端的事。

重建某几档索引，直接往 `jobs` 插一条 `history.universe`（这条作业没有 HTTP 入口，是故意的）：

```sql
INSERT INTO jobs(id,owner_id,kind,dedupe_key,body,status,queue,run_after)
VALUES (gen_random_uuid(),'<owner>','history.universe','usd_m:1h:w96-192',
        '{"market":"usd_m","interval":"1h","top":200,"windows":[96,192]}','queued','batch',now());
```

`windows` 给哪几档就只建哪几档，不给就是五档全建；一条作业只做一个周期。作业每 45 秒让出队列、把进度写进 `public_market.universe_index_runs`，状态在 `jobs` 里表现为 `retry_wait` + `error_code=universe_index_step_yielded`，这是正常的续跑，不是失败。校准作业同理：

```sql
INSERT INTO jobs(id,owner_id,kind,dedupe_key,body,status,queue,run_after)
VALUES (gen_random_uuid(),'<owner>','chart.calibrate','calib-1h-v1',
        '{"interval":"1h","samples":500}','queued','batch',now());
```

跑完的分位数写在 `jobs.result` 里（每档 `samples/available/skipped` 和 `p50/p60/p85/p97/max`）。**先建索引再校准**：某一档一行特征都没有时，那一档的 `available` 是 0、量不出分布，那一档的稀有度就一直是 `null`。

匹配完成后使用候选的 chart_request 再取数据，绘图请求的 match_end_at 标明原匹配结束位置。后续 32/64/128 根仅用于展示，不能影响召回、评分、排序。仅画真实已收盘 K 线，未来不存在就明说。候选指定 REST 或官方归档来源，不能静默换源。

## 历史范围与资源

索引 `/v1/history/indexes` 单次最多 50,000 根来源 K 线和 1,000 个窗口，逐批计算、最多每 500 条特征批量写入。长范围用 `/v1/history/plans`，每段最多 512 个窗口起点，按合约生命周期或已核实归档边界裁剪，并记录实际缺口。

“从上线到最新收盘”入口仅读取目录元数据，确认日期后才可显式开始准备，不自动建立订阅。旧目录的 first_seen_at 不是上线时间。目录存在也不等于全部来源数据已经可用；已发布覆盖以 `/v1/history/coverage` 为准。

特征、元数据、索引在 PostgreSQL/pgvector 的磁盘表中；查询只读取所需页并缓存。少量候选 K 线分组取入 RAM，原始行情和系统图不写数据库/文件/离线缓存。向量数越大仍有索引 I/O、缓存和维护成本，不宣称 TB 级单机性能已经验收。

## 取数的形状：候选池有多大、时间花在哪（2026-09-11 实测）

这一节是给以后的人解释「为什么是这些数字」的。以下全部来自同一张真实截图、同一组窗口的实测，不是估算。

**候选池比「预算」这个词听起来小。** ANN 物化出来的 1,000 行，按「每合约最多 3 条不紧邻片段」封顶之后落到 **142 个合约**；`rerank_budget=30` 时最终真的进精排的只有 **25–27 个合约**，不到候选合约的两成。所以把预算从 30 抬到 100 抬的是**广度**——多覆盖几十个合约——不是把同一批合约看得更细。

**成本几乎全是月档的 HTTPS 往返。** 预算 100 的一次检索要拉 **793 个月档文件**（预算 30 时 262 个）。主导的是 256 根 1d 的窗口：一个这样的窗口就横跨 9 个自然月，也就是 9 个文件。整条链路的前段（视觉 + ANN + 来源校验）只花 **1.2 秒**，其中 ANN 那条 SQL 本身**只有 29 毫秒**；此外的时间全在月档上。而文件本身小得可以忽略：1d 月档 **2159 字节**、4h 月档 **10812 字节**，curl 量到 `ttfb ≈ total`。结论很硬：**这里省时间的唯一办法是提高并发，不是减少传输量、也不是省内存。** 从前按 `bounded(response, 64 * 1024 * 1024)` 推出来的「最坏 768MB 内存预算」是拿错了前提——那个上界是防炸的安全网，不是并发要还的账。

并发因此是三层叠的，改任何一个之前先看清另外两个：`chart_search/rerank.rs` 的 `REFETCH_CONCURRENCY` 决定精排这一支同时取几个区间；`history_catalog/archives.rs` 的 `MONTH_CONCURRENCY` 决定单个区间内部的月档铺多宽；真正的总量上限是 `adapters/binance_archive.rs` 的 `KLINE_SLOTS`，所有 `klines()`（含 `history.universe` 的扇出建索引）都在同一个信号量前排队。

**两次改造的实测对照**（同一张截图、同一组窗口）：

| | 改造前 | `c0bf25e` 月档并行 | `6d98aa3` 打开 h2 |
|---|---|---|---|
| 单个 9 月档窗口 | 3.44–3.74s | 0.50–0.65s | — |
| 12 个窗口并发（108 个文件） | 2/12 失败（http 503，卡 62–66s），整批 ~66s | — | 12/12 成功，整批 **1.2–1.3s** |
| 冷 worker 第一次检索 | — | 55.3s（两次 attempt，第一次 30s 后 `archive_download_unavailable` 退避重跑） | **8.2s**，`job_attempts` 只有一条 `succeeded` |
| 热进程检索 | 66.7–68.8s | 9.2s | **7.2s** |

**h2 起作用的直接证据**：突发瞬间峰值张开 43 条 TLS 连接，随即收敛到 **1 条**，108 个文件全在那一条连接上多路复用跑完。冷池第一瞬间仍然会张开几十条连接——reqwest 在第一条连接握手完成前无法把请求并到一起，这一点没被消除，只是代价从 66 秒降到 1.2 秒，不值得再追。

**结果没被动过。** 前三名逐字未变：INJUSDT（窗口起点 2024-04-02）、NEARUSDT（2024-04-02）、ETCUSDT（2023-03-24），`rerank_budget=100`，`windows_dropped_for_unproven_source=0`。延迟改造没有改变排序，这是它该有的样子。

**说清楚这一轮没做什么：只动了延迟，没动准确率。** 分数仍然是 0.40–0.44 这个量级，离下面那条 0.80 的信任阈值还差得远。真正要撬动它的是两件更大的事——`crates/core/src/domain/chart_match.rs` 里 `rerank()` 那个 `×0.25` 的方向悬崖，以及把分数从现在的结构排序改成对着零假设分布的百分位。那是另一件事，而且一旦动了，现有的 0.80 阈值立刻失效，必须配一次全新的盲测才能重新定阈值。

## 索引的广度：按月档扇出（`history.universe`）

刻舟求剑要的是「广」：任意品种、任意周期地找相似结构。库里只有四个品种时，那句「任意」是假的。`history.universe` 作业（`batch` 队列）按 24 小时 ticker 取一个 market 的前 200 个合约，把它们的历史灌进 `public_market.features`。一条作业只做一个周期，这是用户明确要求的分法：粗周期先跑完，检索就能在那一档上工作，细周期什么时候跑由人决定。

名单排序是「24 小时成交额名次 + 24 小时成交笔数名次」两项相加（Borda）后升序，和相同按简称字典序（`application/instrument_popularity.rs`）。只按成交额排，几笔巨鲸单就足以把一个其实没人在交易的合约顶进名单；只按笔数排又会挑出一堆碎单的小票。名单连同每个品种当时的成交额、笔数和两项各自的名次一起存进 `public_market.universe_snapshots` / `universe_members`，作业进度存 `universe_index_runs`：ticker 是快照，前 200 名每天都在变，不存档事后就没人答得出「这一轮到底搜了哪 200 个、截止到哪一天」。

取数只走 `data.binance.vision` 的月度归档，不走 REST。`adapters/binance_archive.rs` 全文没有一处 `budget.reserve`，S3 静态对象不占 fapi 的限频配额——两百个品种、十年历史这件事能做，前提就是这一条。一段范围的月档并发下载一次，解析出来的 bars 直接喂给 64/128/256 三档窗口（`STRIDE=4`）各建一个世代，而不是每档各下一遍同一个 zip。作业每 45 秒（`STEP_BUDGET`）把进度写下来、让出队列。归档里缺一个月是常态（新币、下架、币安漏传），记进 `failures` 继续走。一根 K 线都不落盘，写下的仍然只有向量和时间坐标。

这条路目前**没有 HTTP 路由，openapi 里也没有条目**：作业靠直接往 `jobs` 插一行来排（kind `history.universe`，体里给 `market`/`interval`/`top`），入口是故意押后的。

## 当前运行决定与验收

按用户 2026-09-10 最新要求，只交付功能，不启动历史同步。实际测试用 BTC/ETH 两品种、1h/4h 两周期、每范围 512 根近期真实 K 线，另测 BTC 上线附近 128 根 1h K 线。193 条临时特征通过同周期检索与后续图验证后，隔离库与临时目录立即删除。

上面那句「不启动历史同步」说的是**滚动订阅**，这一条至今没变；但「公共特征和覆盖均为 0」从 2026-09-11 起不再成立：`attachment.locate` 的按需建索引和 `history.universe` 的月档扇出都会往公共索引里写行，后者是人一条一条排的作业，不是订阅。下面是 2026-09-11 当天 1d 补跑和 4h 首轮扇出**都跑完之后**的实测，是那一刻的事实、不是承诺：

- `public_market.features` 已发布的行：4h 569915、1d 79374、1h 16394、30m 1881、3d 1633。
- `public_market.coverage_segments` 的 1d 部分共 942 行，但**行数不是段数**：一个工作单元会给 64/128/256 三档窗口各建一个世代，而这张表按 `generation_id` 记，所以同一个 `(symbol, start_at, end_at)` 最多占三行。按单元去重后是 401 个单元、187 个品种，其中 221 个 `complete`、180 个 `partial`。拿 942 这个行数去分类会把同一个单元数三遍，得出来的结论是错的。
- 那 180 个 `partial` 单元分两种，两种都**不是**「重跑就能补上」：166 个是某品种最早的一段、`actual_start` 就是它的上线日期，照实截断；另外 14 个全部是 `2022-01-01..2024-01-01` 这一段（SOLUSDT、XRPUSDT、LTCUSDT、TRXUSDT 等），月档一个没掉、首尾都顶到范围两端，断的是中间——币安自己的 `2022-02` 归档只到 2 月 25 日、`2022-04` 归档从 4 月 3 日才开始，缺的 5 天在上游就没有。
- 4h 首轮扇出（作业 `9fcae645`）200/200 跑完，用时 1 小时 36 分，下了 4832 个月档，建 3729 个单元、跳过 914、失败 11，写入 506567 行特征。按单元去重后 **196 个品种、1408 个单元，全部 `complete`**，没有一个 `partial`——其中 193 个单元的 `actual_start` 晚于范围起点，那是上市晚，不是缺口。`features_usd_m_4h` 这个分区此刻 1607 MB。
- 那 11 条失败收敛成三类：`flat_chart_geometry` 10 条（3 个品种，K 线太平，几何特征算不出来）、`archive_not_available` 3 条（MARSCOINUSDT、PONSUSDT、哈基米USDT，上市太新还没有月档）、`archive_catalog_unavailable` 1 条（ASTERUSDT）。这四个品种一根都没进去，196 而不是 200 就是这么来的。
- **3d 已经补过扇出（作业 `02d3c687`，2026-09-11 11:49–11:53，4 分 23 秒）。** 200 个品种里建了 129 个单元、跳过 18，下了 1614 个月档，写入 1604 行特征。加上原有的 29 行，3d 此刻共 1633 行：`bars_count=64` 1161 行 39 个品种、`bars_count=128` 443 行 26 个品种、`bars_count=32` 29 行 1 个品种（那 29 行是从前一次临时索引请求的副产品，只有 BTCUSDT）。64 和 128 都在跨品种检索绑的 64/128/256 三档里，所以**刻舟求剑的候选池从这一刻起收得到 3d**；`bars_count=32` 那 29 行仍然只有重温够得着，单品种那条路径（`history.rs:509`）不过滤 `bars_count`。
- 3d 的 `failures` 数组有 50 条，全在 `listing` 这一步：49 条 `archive_not_available`、1 条 `archive_catalog_unavailable`。同一份回执里的 `units_failed` 却是 5，两个数字对不上——这是 `universe.rs` 里早就记下的计数口径不一致（`tally` 按单元数，`failures` 按品种记），**以 50 为准**：listing 失败发生在任何单元成立之前，那一刻还没有单元可以计。200 个品种只有 39 个拿到了行，不是我们漏跑，是币安 Vision 上多数合约根本没有 3d 的月档目录——这是上游的盘子就这么大，重跑不会变多。4h 有 195 个品种、3d 只有 39 个，这个落差要照实记着，别把「3d 搜不出东西」当成检索出了毛病。
- `replay_bars` 131 行（一次性展示缓存，带 `expires_at`，与索引无关）；`history_subscriptions` 0 行。

## 质量：真实截图盲测（2026-09-11）

`ops/blind_test.py` 分两轨跑：合成轨拿库里已知答案的窗口重新截图回查（有真值），真实轨拿用户那 14 张真实截图跑（无真值，只能看分数落在哪）。要 Pillow，系统 `python3` 没有，用 `vision/.venv/bin/python ops/blind_test.py`。

结论按可信度从高到低：

- **0.80 是当下该用的信任阈值，不是 0.70。** 在合成轨上，0.80 放过 27/54 条 top-1 正确的，放过 **0** 条 top-1 错误的（共 150 条），也放过 **0** 条负对照（共 23 条，那些是库里根本没有对应结构的图）。降到 0.70 就不行了：负对照的分数中位数是 0.617，0.70 的通过带里已经坐着它们。宁可让一半正确答案说「不确定」，也不能让一条负对照冒充答案。
- **所有 14 张真实截图都落在 0.327–0.528。** 一张都够不到 0.80。所以对真实截图，系统今天诚实的回答是**「不知道」**，不是给一个排第一的品种。这既可能是索引广度不够（4h 才刚扇出完，1h/30m 还很薄），也可能是真实截图和合成截图之间有系统性的分布差，盲测本身分不开这两件事。
- **每一个命中率都是有条件的：11.8% 的合成样本在解析阶段就失败了**，它们从未进入打分。分母是「解析成功的那些」，不是「全部」。1h、30m、4h 的同品种数字样本太少，**不可用**，不要引用。
- 「八百万行」那个规模数字是**外推**，不是实测。

### 复跑（同 seed，语料更大）：渲染条件比打分函数更要命

2026-09-11 在 `90d771b` 上用同一个 `--seed 20260911` 又跑了一遍，跑在隔离实例里（容器 `blindtest-pg`，`127.0.0.1:55533`，`target/debug` 二进制），live 库一行没动。**两轮不能逐行对照**：中间语料涨了（这一版快照 4h 已经 195 个品种、64 根那一档 219,808 行），有效试验从 204 条变成 129 条，top-1 正确占比 26.5% → 19.4%。海里草多了针更难找，这是预期内的；但旧语料已经不存在，我没法证明它只有这一个原因。

能对照的是结论，结论复现了：

- **0.80 仍然是该用的阈值。** 0/104 条 top-1 错误的过线，0/20 条负对照过线；降到 0.70 就有 3/20 条负对照过线。负对照最高分中位数 0.6257（上一轮 0.617）。
- **14 张真实截图落在 0.334–0.53**，还是一张都够不到 0.80（上一轮 0.327–0.528）。
- 解析阶段失败 15/144 = 10.4%，全是 `chart_obstructed_or_unsupported`。下面的命中率仍然是「在图能被解析的前提下」的。
- 1d（187 个品种，唯一有广度的一档，n=72）：精确 id top-1 15.3% / top-30 27.8%；同品种 top-30 72.2%，随机基线 16.0%；漏检 27.8%；命中时名次中位数 1.0。

**这一轮真正新的东西是：截图长什么样，比打分函数里任何一个系数都更能决定找不找得到。** 1d 那 72 条按渲染条件拆开（报的是近似命中 top-30，即同品种同周期 ≥90% 重叠）：

| 条件 | n | top-30 近似 |
|---|---|---|
| 成交量副图 有 | 40 | **12.5%** |
| 成交量副图 无 | 32 | **65.6%** |
| 指标副图 有 | 13 | 15.4% |
| 指标副图 无 | 59 | 40.7% |
| 均线 2 条 | 19 | 57.9% |
| 均线 3 条 | 38 | 26.3% |
| 缩放后宽 800 | 26 | 53.8% |
| 缩放后宽 1600 | 14 | 14.3% |

成交量副图这五倍的差距不是别的变量混进来造出来的假象。分层看它在每一层里都在：

| 分层 | 有成交量副图 | 无成交量副图 |
|---|---|---|
| 无指标副图 | 3/27 | 21/32 |
| 均线 3 条 | 2/23 | 8/15 |
| 缩放后宽 ≤1200 | 2/20 | 17/19 |
| 64 根 | 2/17 | 9/9 |
| 128 根 | 1/13 | 8/12 |
| 256 根 | 2/10 | 4/11 |

机制上最可能的解释在 `crates/core/src/domain/chart_match.rs:145` 那段「把主图蜡烛和成交量副图分开」的逻辑。它的判据是「这一排里有没有三分之二共用同一条底边」，可主图蜡烛和它的成交量柱落在同一个 x 上，`row.dedup_by` 先把它们并成一根，判据看到的于是是混合之后的那一排，闸门形同虚设。两条实测旁证：

1. **有成交量副图时检出区域反而更高**，七种机身无一例外（`phone_portrait` 0.790 → 0.864，`tablet` 0.796 → 0.840，占的是最终图高）。真把副图切掉的话应该矮掉约 17% 才对。
2. **检出根数会超过真值**：64 根的图检出过 67、70、76、79。多出来的只能是某些列里蜡烛漏检、底下的成交量柱顶了上来。

只要混进来一列，`normalized()` 的 min–max 就把整段价格压进上面一小条，几何随之报废——而检出根数和间距一致性看着都还健康，所以这个毛病在质量指标上完全隐身。这条机制还没被直接证死，证死它的办法就是修完重跑盲测，看两组收不收敛。

为什么这件事分量重：币安 App 默认就带成交量副图，用户那 14 张真实截图基本都是这个样子。所以「真实截图全都到不了 0.80」，很可能不全是索引广度不够的锅。

### 修完副图分离之后：同一份快照上的前后对照（`c051f4f`）

`crates/core/src/domain/chart_match.rs` 把「共用底边」的判据提到按列去重之前、整片剔掉柱状副图之后，用**同一个 seed、同一份快照**（语料表逐格相同，所以这一次是真能逐行对照的）重跑：

| 1d 正文（n 72 → 71） | 修前 `90d771b` | 修后 `c051f4f` |
|---|---|---|
| 精确 id top-1 | 15.3% | **28.2%** |
| 精确 id top-30 | 27.8% | **46.5%** |
| 近似 top-1 | 22.2% | **38.0%** |
| 近似 top-30 | 36.1% | **59.2%** |
| 同品种 top-30 | 72.2% | 83.1% |
| 漏检 | 27.8% | **16.9%** |

因果链是干净的：**带成交量副图那 39/40 张从 12.5% 涨到 53.8%，不带副图那 32 张纹丝不动、仍然是 65.6%**（逐张比对，检出根数一根没变）。五倍多的差距收敛到 1.2 倍。剩下的那点差距和 11 张仍然超额检出，查下来主要不是副图残留，而是右侧盘口深度条、红绿价格标签这类噪声——那是另一个独立缺陷。

阈值结论不变：0.80 仍然放过 0/86 条 top-1 错误的、0/20 条负对照；0.70 仍然放过 3/20 条负对照。变好的是产出——过线的正确答案从 16 条变成 22 条。

两处代价，都记在这里：

- **解析失败 15 → 18**（新增 BNBUSDT 1d、DOGEUSDT 1d、ALGOUSDT 4h、BTCUSDT 30m 四张，恢复 1 张）。这四张修前就已经是漏检，所以命中率一分没掉；变化是从「悄悄给一组错的几何」变成「明说解析不了、请框选区域」。
- **对用户那 14 张真实截图几乎没用**：只有 `896babc3` 一张变了（VELVETUSDT 4h 0.417 → XMRUSDT 4h 0.598），区间从 0.334–0.53 变成 0.334–0.598，仍然没有一张够到 0.80。所以上一节里「币安 App 默认带成交量副图、用户那些图基本都是这样」是推测，实测不支持它——真实截图够不到阈值另有原因，还没查出来。

## 规模：验到哪儿为止

单分区 200 万行是实测验过的；维护成本的拐点出现在 66 万行附近（HNSW 索引重建和 `VACUUM` 的时间在那之后明显抬头）。**千万行以上没有验收过**，不要引用任何号称 TB 级或亿级的结论。

运维上有一条硬约束：重建 `public_market.features_*` 上的 HNSW 索引只能**串行**做，一次一个分区。Postgres 容器的 `/dev/shm` 是 1.0G，并行重建会在那里撞上限然后失败。

数字会过期，查询不会。要当下的实况，自己跑这几条：

```sql
SELECT timeframe, count(*) FROM public_market.features WHERE published GROUP BY 1 ORDER BY 2 DESC;
SELECT count(*) FROM replay_bars;
SELECT status, count(*) FROM history_subscriptions GROUP BY 1;   -- 滚动的历史订阅有没有开
-- 覆盖按单元算，不按行算；并把 partial 拆成「上市晚」和「上游归档有缺口」两类
-- 换 timeframe 就能看别的档
WITH u AS (
  SELECT DISTINCT ON (symbol, start_at, end_at)
         symbol, start_at, end_at, actual_start, status
  FROM public_market.coverage_segments WHERE market='usd_m' AND timeframe='1d'),
n AS (SELECT *, row_number() OVER (PARTITION BY symbol ORDER BY start_at) AS no FROM u)
SELECT status,
       count(*) FILTER (WHERE no=1 AND actual_start>start_at) AS listed_late,
       count(*) FILTER (WHERE NOT (no=1 AND actual_start>start_at)) AS other,
       count(*) AS units
FROM n GROUP BY status ORDER BY status;
-- 某一轮扇出的失败都是什么原因
SELECT f->>'code', count(*), count(DISTINCT f->>'symbol')
FROM public_market.universe_index_runs r, jsonb_array_elements(r.failures) f
GROUP BY 1 ORDER BY 2 DESC;
```

用户原图、记录和复盘保留。2026-09-10 的清理证据见 period-live-verification.json、public-history-cleanup.json——它们记的是那一天的状态，不是现在的。「币安全部历史已建成」的覆盖结论仍然没有发布，也不该发布：4h 一档 196 个品种不等于全部历史。


## 2026-09-12 最终校准与联合检索修订

迁移 0053 将校准按 `pipeline` 分开：旧记录保留为 `legacy-top3`，线上只读取 `public-search-300-v1`。正式校准复用公开检索的候选初筛、精排 300 与来源验证，排除样本自身及邻近重叠窗口。每条样本以 `sample_id` 持久化去重；每步最多尝试 4 个样本，约 45 秒让出队列，worker 重启后从已有样本继续。只有同周期最近档位满 **500** 个有效样本才使用稀有度；不会借别的档位或把旧 top3 样本混入。未达标返回 rarity=null，按绝对分数显示。`chart_calibration_progress` / retry_wait 是正常续跑。作业参数为 interval、buckets、samples、market；不再支持通过 candidates 降低正式精排预算。

`ChartSearchInput.query_text` 是可选文字约束：仅支持 private 范围，去除首尾空白后最多 4096 UTF-8 字节，空串等于未填写。带文字的公开行情请求返回 422 `chart_query_text_requires_private_scope`。私库在候选预算和截断前融合 BGE-M3 语义、词法与图形召回，受 owner/cutoff/dirty source 状态约束；返回 `text_match` 的来源身份、版本、片段及排序依据。图形 match.score 保留原义，不伪装为语义匹配度或胜率。

公开精排请求为扫窗补取相邻区间时，若跨入尚未发布的月档，先退回原索引窗口核验；原窗口也不存在时仅排除该候选组。失败不会变成伪造行情，也不会令其他合法候选整轮失败。
